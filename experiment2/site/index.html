A feasibility study

Is any Polymarket wallet worth following?

Can you make money copying a wallet's bets? Only if its edge is in being right about outcomes (copyable), not trading the price (not copyable) — and only if that edge persists out-of-sample. This study is the feasibility gate: five parts, from raw on-chain fills to an honest verdict.

Verdict: Yes — but the edge is small, lumpy, decays gradually over at least half a year without fully disappearing, and cuts both ways (avoiding bad wallets and picking good ones are comparably useful). Genuine steady compounders are ~1% of holders.

THE FIVE PARTS

Read in order

Part 1 — Decomposition Split every position's profit into trading vs holding, via FIFO, on real fills. Interactive.
Part 2 — Aggregation Roll up to wallets; the trading_share key variable; is the split bimodal? (No — one continuum.)
Part 3 — Survivorship Add the losers back: a PnL-neutral cohort sampled from 6,347 wallets, 2,055 qualify (59% losers) via activity sampling.
Part 4 — Persistence The central test: does the edge survive out-of-sample? Consistency, equity curves, decay.
Part 5 — Verdict The five questions answered honestly, with strategy implications and all caveats.

Discoveries worth keeping

Things we learned the hard way — data quirks, decisions, and bugs — so they aren't lost.

Data-source decisions

sourceGoldsky order-book subgraph = the spine

Full per-fill history (both maker & taker), queryable per wallet. Legacy subgraphs stop at the 2026-04-28 v2 migration — the study's hard data cutoff. See probes/ and the memory note polymarket-data-access.

rejectedlum.id findata = taker-only tape → excluded

Its per-market trades endpoint is a taker tape (one row per print, labeled with the taker only — no maker). It's also a forward-capture starting ~May 2026. Splicing it onto the both-legs subgraph at the April seam would manufacture a false edge-decay artifact. Full probe results: probes/FINDATA_API_REFERENCE.md.

proxyNo resolution timestamp anywhere

The pnl-subgraph Condition has only payout numerators. Resolution dates come from CLOB end_date (bulk /markets endpoint, ~881k markets) as a proxy — the main methodological assumption of Part 4.

Data quirks & modelling choices

quirkCTF split/merge is invisible to the fill log

Minting a set ($1 → 1 YES + 1 NO) isn't an order-book fill, so wallets that mint then sell appear to "sell more than they bought" (oversold, no cost basis). This is the 34.0%-volume exclusion and it's concentrated in market-makers. We chose not to model CTF (they aren't followable anyway) but report the size.

quirkHedge flag catches sequential flips too

"Bought both YES and NO, ever" flags simultaneous hedges and sequential flips (bought YES, sold, bought NO) alike. Sampling showed ~41% of hedged pairs are flips by count, but only ~18% by dollars — small impact, left as-is.

choiceFIFO primary, VWAP as a robustness check

Every position is decomposed both ways; conclusions don't change between them. Sell-at-resolution tolerance uses price triggers (>0.97 / <0.03); the "within 60 min" trigger was uncomputable (no resolution timestamp).

insight"Holder by profit" ≠ "held everything"

61% of pure holders held <80% of their capital to settlement — they churn a core position at break-even, so trading_share ≈ 0 while holding_fraction_dollar is lower.

Bugs found & fixed (in lib_subgraph.py / lib_recon.py)

bugPython-3.9 socket.timeout escaped the retry loop

It isn't a TimeoutError subclass in 3.9, so read-timeouts crashed the fetch. Fixed by catching socket.timeout/OSError explicitly.

bug92 MB written to disk per wallet

resolve_tokens re-saved the full token+condition caches on every call. Made the save conditional (only on change) and memoized the load — turned a ~2 h run into minutes.

bugCache corruption from a mid-write kill

Killing a run during a non-atomic json.dump truncated cond_payout.json. Recovered by salvaging the valid prefix (129,792 of ~262k entries) + self-heal. Cache writes are now atomic (temp + rename), so it can't recur.
